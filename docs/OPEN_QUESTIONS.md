## Later algorithm decisions already visible in the brief

- Phase 3 acceptance now has an executable report: `pnpm routing:golden` deliberately exits 1 with source and per-item mismatches. A passing regression suite verifies conservative behavior; it does not waive golden acceptance.
- Phase 3 conditional rows: resolve Items!AC versus AG before membership/skincare conditions become advice. The explicit conflict list is in `packages/engine/src/route/source-conflicts.ts`; ambiguous rows stay T3 with cost shown, unless an earlier independent rule settles them.
- Phase 3 worked-example inputs: what is the fish-oil goal? The example gives only dose; general health would stop at step 3. Are the 9pm workouts vigorous, and how long before bed do they end? The rule requires both, so four evening sessions alone do not authorize T1.
- Phase 3 skin overlap thresholds: define “used least” and “less than weekly” in exact observations, including what to do when all devices are in use. Current comparisons stay pending; no weekly frequency is guessed from a partial month count.
- Phase 3 Protected custom items: a declared wearable data source can be Protected without inventing a catalog row. Its cost enters the total only by an explicit include choice; its routed output has no cost or recommendation.

- `[3,3,3,3,2]` cannot be assigned into equal seven-night sides: no subset sums to seven. Phase 4 implements `[3,3,3,3,1,1]` normally and `[3,3,4,4]` for carryover, with exhaustive constraint checks. These reconcile the starting constraints; simulation has not validated them.
- Phase 5 decision resolved with the project owner's approval: new registrations use `both_directions`, with the overall 0.05 budget split into 0.025 per tail. Existing registrations without a policy retain `benefit_only` at 0.05 and cannot receive an opposite-direction drop. Policy and raw baseline snapshots are immutable after start. [ALGORITHM.md](ALGORITHM.md) contains the full decision table. Simulation validation remains pending.
- Removing the first night from each of five blocks leaves nine valid nights, below the required five per side. The Phase 4 carryover layout has four blocks and five usable nights per side before missing data. Actual compliance/exclusions can still make a result inconclusive.
- Phase 4's exact default assignment spaces contain only six assignments normally and two with carryover. Their minimum one-sided p-values are 1/6 and 1/2, so neither supports either statistical policy. Phase 5 enforces Inconclusive. The earlier 22-assignment long example can support the benefit-only threshold in principle, but not the new 0.025 thresholds. Explicit layouts with 60 or 138 assignments are documented for Phase 6 comparison, not adopted as defaults. Carryover can erase one-day blocks and create tied assignments even in a larger space.
- Phase 5 deliberately treats observational experiments as descriptive comparisons, with no randomization test or causal Kept/Dropped decision. Is a separate observational decision policy wanted later? It needs an explicit design for confounding; Phase 7 should label these results observational.
- Phase 5 suppresses randomized inference when actual usable exposure contradicts assignment, rather than permuting actual behavior as though it was randomized. Should a future protocol analyze the effect of instructions (intention to treat), or introduce another noncompliance estimator? Missingness/exclusion assumptions and bootstrap interval coverage must also be evaluated in Phase 6.
- Legacy Phase 4 baseline records lack raw value snapshots. Phase 5 requires history on the saved dates/channel to reproduce their saved MAD, otherwise returns Inconclusive. The old MAD cannot establish that every original value is unchanged; new registrations save all baseline values before starting.
- The brief's “Phase 1–5 done” acceptance references simulation from Phase 6. That evidence now exists, with the following limitations before overall algorithm acceptance.

## Phase 6 findings and decisions

- The full report records 105,500 attempted experiments. Original 14-day layouts have zero power. The explicit 42-day reference has 38% power at 0.8 swings and 70.4% at 1.2. Should the app offer 28 days with two-day blocks, 42 days with three-day blocks, or a duration choice? Both are measured in [POWER.md](POWER.md). The saved default stays unchanged; the reference config is exported for explicit use.
- The 0.8 gate remains a priority rule. [power-labels.json](../data/power-labels.json) compares all 210 source rows without rewriting the workbook. Estimates apply only to fast randomized outcomes/effects actually simulated; unresolved or multi-metric rows are unavailable. Good/fair/low use the Monte Carlo lower bound at 50% and one-third. Source fact-check flags and literature estimates remain unchanged.
- Independent missingness scenarios have false positives around 5%, with Monte Carlo uncertainty. Deliberately omitting bad on-nights produces 11.1% false positives (95% interval 9.8–12.6%). How should the real-user protocol address informative missing answers? Fixed, assignment-independent exclusions remain an assumption; simulations do not establish that behavior in actual users. A different estimator/design needs its own validation.
- Nominal 90% bootstrap coverage is about 84.4–89.6% across tested profiles. Public cards now hide the interval with `intervalStatus: coverage_not_established`; internal intervals remain for diagnostics. A replacement requires a defined estimand and fresh coverage checks without changing saved decision rules.
- The three demo identities are isolated local fixtures with six calendar months of history and a read-only API. Phase 8 must add the actual clickable screens and choose hosted demo provisioning. The seed does not create real Supabase sign-in users or deploy data.
