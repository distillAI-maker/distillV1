## Later algorithm decisions already visible in the brief

- Phase 3 acceptance now has an executable report: `pnpm routing:golden` deliberately exits 1 with source and per-item mismatches. A passing regression suite verifies conservative behavior; it does not waive golden acceptance.
- Phase 3 conditional rows: resolve Items!AC versus AG before membership/skincare conditions become advice. The explicit conflict list is in `packages/engine/src/route/source-conflicts.ts`; ambiguous rows stay T3 with cost shown, unless an earlier independent rule settles them.
- Phase 3 worked-example inputs: what is the fish-oil goal? The example gives only dose; general health would stop at step 3. Are the 9pm workouts vigorous, and how long before bed do they end? The rule requires both, so four evening sessions alone do not authorize T1.
- Phase 3 skin overlap thresholds: define “used least” and “less than weekly” in exact observations, including what to do when all devices are in use. Current comparisons stay pending; no weekly frequency is guessed from a partial month count.
- Phase 3 Protected custom items: a declared wearable data source can be Protected without inventing a catalog row. Its cost enters the total only by an explicit include choice; its routed output has no cost or recommendation.

- `[3,3,3,3,2]` cannot be assigned into equal seven-night sides: no subset sums to seven. Phase 4 implements `[3,3,3,3,1,1]` normally and `[3,3,4,4]` for carryover, with exhaustive constraint checks. Phase 6 confirms these layouts have zero decisive power under the saved decision policies.
- Phase 5 decision resolved with the project owner's approval: new registrations use `both_directions`, with the overall 0.05 budget split into 0.025 per tail. Existing registrations without a policy retain `benefit_only` at 0.05 and cannot receive an opposite-direction drop. Policy and raw baseline snapshots are immutable after start. [ALGORITHM.md](ALGORITHM.md) contains the full decision table. Phase 6's simulation evidence and limitations are documented below and in [POWER.md](POWER.md).
- Removing the first night from each of five blocks leaves nine valid nights, below the required five per side. The Phase 4 carryover layout has four blocks and five usable nights per side before missing data. Actual compliance/exclusions can still make a result inconclusive.
- Phase 4's exact default assignment spaces contain only six assignments normally and two with carryover. Their minimum one-sided p-values are 1/6 and 1/2, so neither supports either statistical policy. Phase 5 enforces Inconclusive. The earlier 22-assignment long example can support the benefit-only threshold in principle, but not the new 0.025 thresholds. Explicit layouts with 60 or 138 assignments are documented for Phase 6 comparison, not adopted as defaults. Carryover can erase one-day blocks and create tied assignments even in a larger space.
- Phase 5 deliberately treats observational experiments as descriptive comparisons, with no randomization test or causal Kept/Dropped decision. Is a separate observational decision policy wanted later? It needs an explicit design for confounding; Phase 7 now labels these results observational and Inconclusive.
- Phase 5 suppresses randomized inference when actual usable exposure contradicts assignment, rather than permuting actual behavior as though it was randomized. Should a future protocol analyze the effect of instructions (intention to treat), or introduce another noncompliance estimator? Phase 6 evaluated missingness/exclusion assumptions and bootstrap interval coverage; their limits are recorded below.
- Legacy Phase 4 baseline records lack raw value snapshots. Phase 5 requires history on the saved dates/channel to reproduce their saved MAD, otherwise returns Inconclusive. The old MAD cannot establish that every original value is unchanged; new registrations save all baseline values before starting.
- The brief's “Phase 1–5 done” acceptance references simulation from Phase 6. That evidence now exists, with the following limitations before overall algorithm acceptance.

## Phase 6 findings and decisions

- The full report records 105,500 attempted experiments. Original 14-day layouts have zero power. The explicit 42-day reference has 38% power at 0.8 swings and 70.4% at 1.2. Should the app offer 28 days with two-day blocks, 42 days with three-day blocks, or a duration choice? Both are measured in [POWER.md](POWER.md). The saved default stays unchanged; the reference config is exported for explicit use.
- The 0.8 gate remains a priority rule. [power-labels.json](../data/power-labels.json) compares all 210 source rows without rewriting the workbook. Estimates apply only to fast randomized outcomes/effects actually simulated; unresolved or multi-metric rows are unavailable. Good/fair/low use the Monte Carlo lower bound at 50% and one-third. Source fact-check flags and literature estimates remain unchanged.
- Independent missingness scenarios have false positives around 5%, with Monte Carlo uncertainty. Deliberately omitting bad on-nights produces 11.1% false positives (95% interval 9.8–12.6%). How should the real-user protocol address informative missing answers? Fixed, assignment-independent exclusions remain an assumption; simulations do not establish that behavior in actual users. A different estimator/design needs its own validation.
- Nominal 90% bootstrap coverage is about 84.4–89.6% across tested profiles. Public cards now hide the interval with `intervalStatus: coverage_not_established`; internal intervals remain for diagnostics. A replacement requires a defined estimand and fresh coverage checks without changing saved decision rules.
- The three demo identities are isolated local fixtures with six calendar months of history and a read-only API. Phase 8 must add the actual clickable screens and choose hosted demo provisioning. The seed does not create real Supabase sign-in users or deploy data.

## Phase 7 copy decisions and remaining review

- The project owner selected accurate wording variants with the originals preserved. All 17 original templates still fill exactly. The high-level renderer defaults to contextual copy; strict exact mode withholds text where its claims are incompatible. [VERDICTS.md](VERDICTS.md) lists the cases and API contracts.
- A statistically decisive drop need not exceed one personal swing, and abandoning a restriction does not imply removing a monthly charge. Contextual copy uses “against” when needed and requires an explicit actual-charge flag before promising savings. Use duration/source context is never inferred from wearable history.
- Inconclusive does not establish no effect. Large changes, incomplete schedules, insufficient nights, noncompliance, missing baseline, assignment resolution and legacy untested directions get accurate explanations. Observational results remain observational and Inconclusive.
- The Protected source template has two sentences and assumes a clinician for every protected reason. It remains available for exact source review; the public adapter uses one neutral sentence with the actual doctor/blood-test/data-source context. Missing thresholds/evidence or unresolved source branches yield a structured context/review requirement instead of invented copy.
- Source fact-check sign-off and whether unverified T2 advice is displayed remain team/Phase 8 decisions. Flags survive text rendering; no evidence is newly validated or source workbook rewritten by this phase.

## Algorithm identity (2026-10-08)

Decisions made while replacing the verdict engine; see [ALGORITHM-IDENTITY.md](ALGORITHM-IDENTITY.md) and [DECISION-POWER.md](DECISION-POWER.md).

| ID | Decision |
| --- | --- |
| DECISION_POLICY | New experiments use the estimate-based policy `estimate_v2` (night-level estimate, AR(1)-aware uncertainty, zero-centred prior, 97.5% directional bar, "does nothing" at day 28 when a worthwhile benefit is under 20% likely). The exact randomization test stays only for experiments registered before this change; simulation showed it has zero power at 14 days by construction. |
| ADAPTIVE_SCHEDULE | Every new experiment is registered as 28 days, balanced within the first fortnight, read at days 14, 21 and 28, and stopped at the first decisive read. The product promise becomes "a first read at fourteen days, a verdict by twenty-eight". |
| AS_TREATED | A "didn't" tap flips that night's exposure and the night counts. Noncompliance is recorded as a share, not a blocker. Observed items (alcohol-style) get weekday-balanced contrasts and a 25% wider standard error instead of being refused a decision. |
| LITERATURE_PRIOR | The catalogue's expected effect and evidence grade are recorded in the registration but do not lean on the verdict (prior mean 0). The first draft let them lean and produced about 20% false "costs you" calls on null items; the draft's results are kept at `/tmp` only, the retuned results are in DECISION-POWER.md. |
| COLUMN_CONFLICTS | Resolved by the routing-table owner: the 22 rows whose conditions lived in the goal-notes column now have typed rules in `rules/items.ts` (`resolvedFromGoalNotes`). The workbook's rule column for these rows is superseded by the code. The sleep-coach row stays Protected as the catalogue says. |
| DROP_BEFORE_GOAL | A drop settled by dose, form, evidence or mechanism, and an item not being used, now hold whatever the goal is and need no goal: 300 mg of fish oil is below the studied dose for every reason a person takes it. The hormone goal keeps its clinical precedence. Start Here step 3 ("goal known?") now sits after these checks. |
| MULTI_GOAL | An item without its own goal is routed under each of the person's goals in order; the first goal that settles it (drop, test, keep) wins. |
| WORKED_TOTAL, WORKED_COUNTS, WORKED_ORDER | The Worked Example table is the source and its prose is superseded: the headline counts every entered cost ($1,428); the Protected data source is not a can't-measure item (2); observed items rank by expected effect, and coffee is the first *assigned* test. The example's "four evening sessions ending 9pm" are read as hard sessions within two hours of bed; Barry's two visits follow a normal month, so the overlap decides it. The golden check now passes: 21 items, 10 drops, $767 a month back, 4 lined up. |
| RUN_ANYWAY | An item gated as "too small to see" may start when the person chose to run it anyway; the registration records `runAnyway`. |
| DEMO_ENGINE | The signed-out demo no longer serves a fixture. It runs the same engine on a synthetic person from the simulation generator; day 14 usually comes back "too close, one more week" for a one-swing item, and a "skip ahead a week" control (demo only) walks to the verdict. |
| ONBOARDING_LENGTH | Routing on answers costs questions: the demo stack now asks 24 follow-ups (memberships need visits, apps need last use, serums need a form). The product brief caps follow-ups at about eight. Grouping all membership visit counts on one screen, and reading visits from check-in data where a membership is connected, is the open UX decision. |
| FIRST_READ_POWER | With 7 nights a side a 1.2-swing effect is found at the first read about a quarter of the time and by day 28 about three quarters; a null item is wrongly called about 8 to 10 times in a hundred. The team should decide whether a stricter bar (fewer wrong calls, fewer decisions) or a looser one (more decisions, more wrong calls) better serves the guarantee. The policy object makes that a one-line change plus a simulation rerun. |
| DEMO_SERVER | The signed-out demo computes on the server through two server actions (`apps/web/lib/data/demo/actions.ts`): the catalog is a megabyte and the generator pulls in the provider parsers, neither of which belongs in the browser bundle. The browser keeps the taps; the server keeps nothing. |
| DEMO_FIRST_ITEM | The item the first reading runs is written to `dayOne.firstExperiment` when it starts, so the demo (and a verdict the person has acted on) stays on that item. With the Worked Example stack the engine's own first pick is alcohol (observed, too close at day 14 and 21, "does nothing we can see, leaned the other way" at day 28); coffee, if picked, is clear at day 14. |
| HRV_UNITS | HRV is read on a log scale, so the swing is a percentage. The change is now reported in the same unit (percent) in the sentence and on the card, so a verdict never mixes "6 ms" with "17.6%". The nights chart keeps milliseconds. |
